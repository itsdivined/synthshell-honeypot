## Abstract

Scripted SSH honeypots such as Cowrie are useful but often fingerprintable because replies and filesystem state are fixed. Large language model (LLM) honeypots can invent plausible shell text for almost any command, yet they may forget session state, invent details, time out, or depend on paid APIs. This project asks how realistic, consistent, and cost-effective an LLM honeypot is compared with a traditional honeypot, and which type of LLM gives the best balance in a closed lab.

Four systems were compared on identical multi-step sessions: Cowrie (scripted baseline), GPT-4o mini (commercial API), Llama 3.1 8B (local Ollama), and Qwen 2.5 7B (local Ollama). Sessions came from the Magazov et al. (2026) de-identified SSH corpus (Zenodo DOI 10.5281/zenodo.20816078). Twenty sessions were replayed five times to each system (`data/logs/replay_magazov_20sess_runs5.jsonl`). Metrics included delay with bootstrap 95% confidence intervals, commands completed until a defined break, technique labels, and a containment audit for research question four (RQ4).

Cowrie completed a mean of 3.50 commands per session with sub-second delay. Local LLMs were much slower (mean delay ≈51.5 s for Llama, ≈50.4 s for Qwen on successful replies) and completed far fewer commands before break (means 0.20 and 0.17), largely because of timeouts on a ~7.5 GB RAM CPU laptop. GPT-4o mini was skipped for all 350 command rows (no API key). RQ4 containment passed (localhost bind, text-only model output, no host execution). RQ1 fidelity scores remain blank because the Ubuntu ground-truth capture was not available (Docker not installed). The main practical finding is that, on this hardware, Cowrie remained the only reliably fast backend for multi-step Magazov replay, while local 7–8B models were timeout-limited and the commercial API row stayed empty without a key.

**Keywords:** honeypot; large language model; Cowrie; session survival; containment; Magazov corpus

## 1. Introduction

Attackers and scanners routinely probe SSH services. Defenders use honeypots to observe probing behaviour without exposing production hosts. Traditional medium-interaction honeypots such as Cowrie emulate a shell with scripted replies and a fake filesystem. They are stable and cheap to run, but experienced scanners can recognise fixed banners, incomplete command coverage, and inconsistent state.

Generative AI changes the design space. An LLM can produce shell-like text for commands that a script never anticipated. That flexibility may increase engagement, but it also introduces new failure modes: invented file contents, forgotten session state, leaked instructions, slow replies, and dependency on external APIs. Organisations that cannot send session data off-site may prefer small local models; others may prefer a commercial API for quality. Without a repeatable comparison, those choices rest on demos rather than evidence.

### 1.1 Aim

This project compares Cowrie with three LLM honeypot backends under identical multi-step sessions in an isolated laptop lab. The aim, stated in the repository README and project brief, is to assess how realistic, consistent, and cost-effective an LLM honeypot is relative to a traditional honeypot, and which type of LLM gives the best balance.

### 1.2 Scope

Everything binds to `127.0.0.1`. There is no public honeypot and no live attacker traffic generated by this project. LLM backends return text only: the model is not given tools, and commands are not executed on the host operating system. Saved sessions are replayed; replies are logged to JSONL and scored offline.

## 2. Related work

Javadpour et al. (2024) survey cyber deception and honeypot performance in *Computers & Security*, framing why realism and evaluation matter for defensive decoys (doi:10.1016/j.cose.2024.103792). ### 2.2 Generative and LLM honeypots

Sladić et al. (2023) explore LLMs in the shell as generative honeypots (arXiv:2309.00155). A related peer-reviewed EuroS&PW paper (Sladić et al., 2024) provides evaluation context for generative honeypots (doi:10.1109/EuroSPW61312.2024.00054). Wang et al. describe HoneyGPT as an LLM terminal honeypot line of work; the journal version appears in *Computer Networks* (2026) 112223 (doi:10.1016/j.comnet.2026.112223; also arXiv:2406.01882 as cited in the PDM).

### 2.3 Benchmarks and shared traffic

Magazov et al. (2026a) benchmark LLM backends for generative SSH honeypots (*AI*, 7(8), 287; doi:10.3390/ai7080287). That work is the closest published framing for comparing backends and notes gaps around single-command sessions and evaluation designs that this project targets with multi-step, multi-backend replay. Magazov et al. (2026b) also released a de-identified SSH honeypot attacker corpus on Zenodo (doi:10.5281/zenodo.20816078, CC BY 4.0), which supplies the shared realistic sessions used here.

### 2.4 Position of this project

Prior work shows that LLM honeypots are feasible and that engagement/realism matter. What remains scarce is a **repeatable student-lab comparison** in which Cowrie and several LLM backends receive the **same** multi-step sessions, with explicit session-survival scoring, bootstrap intervals, paired tests against Cowrie, local versus API privacy trade-offs, and a documented containment posture. That is the niche this project fills.

## 3. Research gap, novelty, and contribution

### 3.1 Research gap

There is no repeatable multi-step test that compares Cowrie with several LLM honeypots on consistency, session survival, speed, cost, and injection-related resistance under identical conditions. Existing studies often fix one model, send one command per session, rely on small human studies or field deployments that cannot be rerun, and leave invented details, slow replies, prompt injection, and paid APIs weakly measured (project README / brief).

### 3.2 Novelty

LLM honeypots already exist. The novelty claimed here is measurement design, not “first LLM honeypot”:

1. Multi-step, stateful testing with session memory (cwd, file and user deltas).  
2. One repeatable test in which Cowrie and three LLM honeypots receive identical sessions.  
3. Session survival (commands completed until a defined break) as a proxy for engagement, plus technique labels visible to a defender.  
4. Small local models compared with a commercial API for organisations that cannot export data.  
5. RQ4 operationalised as a **containment audit** (local bind, no honeypot outbound channel, text-only output, no host execution). Multi-turn injection was listed as untested in the 2026 Magazov benchmark framing; injection wording is **not** stored in this repository.

### 3.3 Contributions

C1–C4 are listed in Section 1.3. Empirically, this draft delivers C1, C3, and C4 on Magazov traffic; C2 (Ubuntu ground truth) remains incomplete and is treated as a limitation rather than a fabricated result.

**Break definition (used throughout):** empty reply; wrong or contradictory reply; AI self-disclosure; or delay above **5 seconds**.

**Study settings:** 5 runs per system; 95% bootstrap confidence intervals; Wilcoxon signed-rank tests (each LLM versus Cowrie on commands completed when at least five paired sessions exist).

## 5. Methods

### 5.1 Systems under test

| System | Role | Access |
| --- | --- | --- |
| Cowrie | Scripted baseline | SSH on `127.0.0.1:2222` (WSL/local; see `docs/cowrie_localhost.md`) |
| GPT-4o mini | Commercial API | Text-only call to `api.openai.com`; skip if no `OPENAI_API_KEY` |
| Llama 3.1 8B | Local open-weight model | Ollama tag `llama3.1:8b` on `127.0.0.1:11434` |
| Qwen 2.5 7B | Local open-weight model | Ollama tag `qwen2.5:7b` on `127.0.0.1:11434` |

The comparison always keeps **four rows**. A missing key or model is a **skip**, not removal from the study. Safety-critical categories (for example sudo / password-file reads) receive a fixed denial before an LLM call. Cowrie uses its own replies. Session memory (`src/session_memory.py`) stores structured state only; there is no host shell and no tool use.

### 5.2 Data

**Magazov public corpus (verified in `data/MANIFEST.txt`):** Magazov et al. (2026b), Zenodo DOI 10.5281/zenodo.20816078, CC BY 4.0. About 12,881 command rows after download/screen; accessed 25 October 2026; IP screen reported zero public addresses needing review (`scripts/02_screen.py`). Used as shared realistic session traffic.

**Study slice:** `--source magazov --max-sessions 20 --runs 5`, logged to `data/logs/replay_magazov_20sess_runs5.jsonl` (finished 7 November 2026). Analysis: `data/analysis/runs5/`; freeze copy: `data/freeze_2026-11-10/`.

**Ubuntu container test set (planned):** ~200 ground-truth commands and ~20 scripted sessions under `data/test_set/`. On 10 November 2026 these files were still missing. Planned capture used `docker run --rm -it --network none ubuntu:24.04`. Docker was not available on the Windows host; therefore RQ1 fidelity was not computed.

### 5.3 Procedure

1. Containment configuration checks (localhost Cowrie/Ollama, pinned OpenAI host, no host execution).  
2. Replay the same Magazov session list to all four systems via `scripts/04_replay.py`.  
3. Log command, reply, delay, tokens, system, settings, run number, and status (`ok` / `skipped` / `error`).  
4. Score with `scripts/05_analyse.py --log <path> --out-dir <dir>` (bootstrap CIs, Wilcoxon when pairs exist, RQ4 audit).  
5. Freeze Magazov tables for the report (`data/freeze_2026-11-10/`, 10 November 2026).

## 7. Discussion

### 7.1 Trade-offs observed

On this laptop, **Cowrie** offered stable, sub-second replies and the highest session survival under the project’s break definition. **Local 7–8B models** demonstrate the privacy benefit of keeping inference on `127.0.0.1`, but on ~7.5 GB RAM with CPU Ollama they were dominated by timeouts and multi-tens-of-seconds delays. That hardware reality understates what the same models might achieve on a GPU or larger RAM host; it does not justify inventing better numbers. **GPT-4o mini** remains an empty row until a key is configured; keeping the skip is itself an organisational result (no commercial API ⇒ no commercial measurements).

### 7.2 Relation to prior work

Magazov et al. (2026a) motivate careful backend benchmarking and note evaluation gaps around single-command designs. This project responds with multi-step Magazov-session replay and four fixed rows. Generative honeypot systems (Sladić et al.; Otal and Canbaz; Wang et al. HoneyGPT) show that LLM shells can be engaging; this closed-lab design asks a different question: under identical saved sessions and a strict delay break, how far does each backend get, and how safe is the containment posture? The answer here privileges Cowrie for speed/survival on constrained hardware, while affirming that LLM backends can be wired without host execution.

### 7.3 Design recommendation (low-cost)

For a low-cost, no-egress lab honeypot front end: keep Cowrie (or similar) for fast scripted coverage; add a text-only local LLM with session memory only if the machine can meet latency goals; use fixed denials for safety-critical categories; bind only to localhost unless a separate, ethically approved deployment exists. Do not execute model-suggested commands on the host. For commercial quality measurements, provision an API key and price env vars before claiming cost figures.

### 7.4 Threats to validity

Single student laptop; Magazov slice of 20 sessions; break threshold of 5 s; Ollama contention; missing Ubuntu ground truth; GPT skip; RQ4 as containment rather than injection-string benchmark. External validity to live internet attackers is limited by design (isolated lab).

## 8. Limitations

1. **Isolated lab only** — not a public honeypot; limited external validity.  
2. **Ubuntu ground truth not captured** — RQ1 fidelity / invented-content unavailable (Docker missing on 10 Nov 2026; see `docs/remaining_before_freeze.md`).  
3. **GPT-4o mini skipped** — no API key during Magazov ×5; four-system design preserved as skips.  
4. **Local model timeouts** — RAM/CPU limits; delays often exceed the 5 s break rule and/or client timeout (~120 s).  
5. **RQ4 = containment audit** — not a published list of injection payloads.  
6. **Freeze window** — Magazov tables frozen early (10 Nov) ahead of the 14 Nov practical freeze; optional GPT/Ubuntu work may still occur before 14 Nov without overwriting the Magazov freeze package.

## 9. Conclusion

**RQ1:** Realism versus real Linux output was not quantified because Ubuntu ground truth was missing; fidelity cells are blank.  
**RQ2:** Cowrie was fast; local LLMs were slow and often timed out; GPT provided no delay/cost data (skipped).  
**RQ3:** Cowrie completed far more commands before break than Llama or Qwen; Wilcoxon tests on 100 pairs support that difference; eight technique labels are listed in the analysis.  
**RQ4:** Containment audit passed (localhost, text-only, no tools, no host execution).

Contributions C1, C3, and C4 are evidenced in the repository and freeze package; C2 remains future work. Future work: capture Ubuntu ground truth offline, optionally complete a keyed GPT replay into a separate log, and re-test local models on hardware that can meet the 5 s engagement threshold.
